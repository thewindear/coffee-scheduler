# 服务接入、结果订阅与 Worker 管理

## Why

Coffee Scheduler 面向不同语言和业务的服务提供通用 Pull 任务调度。使用者定义任务类型、输入和结果结构。任务完成后，多个服务可以订阅同一结果，各自处理和确认。运行者需要为跨网络实例授权、观察领取情况，并在阻塞或限速时选用合适的租约。

## What Changes

- 用受控管理员 CLI 建立服务身份，签发、轮换、吊销凭证，授权提交方创建任务、执行服务领取任务，并登记、查看、停用下游订阅。
- 将 HTTP 结果订阅持久化。启用结果派发的任务成功时，按业务范围和使用者定义的任务类型确定接收方，每个接收步骤生成独立任务。服务重启后可继续消费积压。
- 启用结果派发的类型允许零订阅者。源任务仍可提交和成功完成，保存完成记录并返回零条派发。
- **BREAKING** 对外结果查询和补跑统一使用任务资源路径及通用字段名，OpenAPI、Python SDK 与示例同步切换。
- **BREAKING** 对外业务与管理 API 默认要求认证，并校验操作权限和资源范围。覆盖普通队列提交与领取、任务管理、死信重试、队列监控、Cron 管理及对外指标读取。
- 增加管理员只读 Worker 查询，展示近期活跃数量、实例 ID、服务、队列、来源 IP 和最近活动时间。
- 通过语言无关的 HTTP/JSON 契约接入 Worker，并在同一仓库交付可独立安装的 Python Worker SDK 与应用示例。任务可选择固定租约或自动续租，耗时操作由客户端执行截止时间约束。

## Impact

依赖同仓库的 `init-coffee-scheduler` 和 `add-result-delivery`。已有 Pull、租约、重试、死信、结果快照、派发和定向补跑是实现基础。本提案将前序方案中的采集类型推广为自定义任务类型，将执行权限推广为按服务授权的队列权限。新增工作涉及 MySQL 接入记录、HTTP 鉴权、结果路由、Redis 活跃状态、运维 CLI 和客户端。首版选择管理员开通订阅；服务自助订阅、全量历史回放和在线历史报表可作为独立需求。
