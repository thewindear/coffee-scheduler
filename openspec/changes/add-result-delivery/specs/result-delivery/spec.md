## ADDED Requirements

### Requirement: 按业务身份提交和授权领取
平台 SHALL 允许已接入的业务方通过 HTTP 按采集类型和业务请求 ID 提交任务，并按认证身份确定归属、允许的操作和内部队列。

#### Scenario: 提交与领取
- **WHEN** 商品业务提交已配置默认处理服务的采集类型，采集 Worker 随后领取任务
- **THEN** 平台返回可追踪的采集任务 ID，授权 Worker 获得执行所需参数，业务方无需配置 Redis 或 Kafka 地址

#### Scenario: 跨业务访问
- **WHEN** 未获授权的服务指定另一业务的队列、任务 ID 或产物引用来领取、查询、确认、读取或补跑
- **THEN** 对应操作被拒绝，任务状态和产物访问权限保持不变

### Requirement: 成功回执与交付意图原子持久化
平台 SHALL 在确认采集成功前，以同一 MySQL 事务提交采集终态、轻量回执、稳定的完成记录 ID 和所有授权接收步骤的待派发记录。采集 Worker SHALL 先保存可读取的产物，再通过现有回执结构提交其引用。

#### Scenario: ACK 提交前失败
- **WHEN** 任一待派发记录写入失败导致事务回滚
- **THEN** 平台不返回成功确认，外部无法观察到仅有部分接收方的完成记录，Worker 可重试

#### Scenario: ACK 响应丢失
- **WHEN** 事务已提交，Worker 未收到响应并以同一次执行重新提交相同回执
- **THEN** 返回原完成记录 ID，每个接收步骤仍仅有一条正常派发记录

#### Scenario: 旧执行迟到
- **WHEN** 租约已被回收并重新分配，旧持有者提交 ACK 或 NACK
- **THEN** 拒绝旧执行的状态变更，不产生交付记录，也不覆盖当前执行或已接受的回执

### Requirement: 按接收服务独立派发与恢复
平台 SHALL 根据完成时固定的接收方、处理步骤和交付方式逐项交付。HTTP 方式下，每个正常派发键 `(completion_id, recipient_service, step)` 对应一个可恢复的处理任务。

#### Scenario: 同一结果有两个接收方
- **WHEN** 采集 A 的快照包含商品 ETL 与质检，之后路由配置发生变化
- **THEN** 两个服务各有一个独立任务，共享原版本产物引用；质检离线或失败不阻塞 ETL，历史派发仍按原快照执行

#### Scenario: 派发进程中断或就绪项丢失
- **WHEN** 派发进程在创建子任务前退出、在持久化后入队前退出，或 Redis 丢失尚待领取的就绪项
- **THEN** 平台从持久记录补建可领取任务，关联到原采集任务，每个接收步骤最终只对应一个正常处理任务 ID，已完成任务不重新入队

### Requirement: 下游处理确认和隔离重试
平台 SHALL 使下游沿用 HTTP 领取、心跳、ACK、NACK、重试和死信机制，并持久记录终态。下游 SHALL 以处理任务 ID 幂等写入业务结果后再确认。

#### Scenario: 业务提交后尚未确认即退出
- **WHEN** ETL 已写入目标库，但在 ACK 前退出且租约到期
- **THEN** 健康实例可以重新领取同一处理任务，识别已有业务结果并确认，最终只有一次业务写入效果

#### Scenario: 单个步骤用尽重试
- **WHEN** 质检处理达到最大重试次数
- **THEN** 该处理任务进入死信，平台可查错误原因；父任务保持采集成功，其他接收方已完成的结果保持有效

### Requirement: 链路追踪与定向补跑
平台 SHALL 支持按父任务查询应交付清单、派发进度、子任务状态及补跑关系，并区分使用原产物重新处理与重新采集。

#### Scenario: 定向补跑质检
- **WHEN** 运维对已失败的质检请求用原产物重新处理，并因响应超时重复发送同一补跑请求
- **THEN** 平台只创建一个新的质检处理任务 ID，关联原质检任务和原完成记录，商品 ETL 和采集均不重跑

#### Scenario: 原产物过期
- **WHEN** 请求补跑时平台已确认指定版本过期或删除
- **THEN** 返回产物不可用的原因，不产生新的采集；调用方可显式请求重新采集并保留与原任务的关系

### Requirement: 业务统计与积压可见性
平台 SHALL 支持按业务方、接收服务和时间窗口查询成功、失败和超时，分别展示采集就绪、结果待派发和下游就绪三段的数量与最老等待时长。端到端超时统计须包含正在执行的下游任务。

#### Scenario: 采集成功但派发进程停机
- **WHEN** 采集和下游 Redis 就绪队列均为空，但有一个成功结果等待派发给两个服务
- **THEN** 待派发积压为两项，各服务可见自己的一项，等待时长从采集成功时间开始计算

#### Scenario: 已领取但未及时完成
- **WHEN** 某个处理任务已经领取且超过配置的端到端期限，之后发生自动重试
- **THEN** 该步骤进入超时统计，自动重试单列计数，不增加正常派发数或成功结果数

### Requirement: Kafka 存量消费方逐步迁移
平台 SHALL 为仍依赖 Kafka 的业务提供内部兼容发布方式，并对每个完成记录的同一接收服务及步骤固定一种正式交付路径。

#### Scenario: 切换时有旧积压
- **WHEN** 某服务从 Kafka 切到 HTTP，切换前仍有待发布记录
- **THEN** 旧记录继续按原消息契约发布，新边界后的完成记录只创建 HTTP 处理任务；回退不改变已固定的路径

#### Scenario: 发布成功但缺少业务回报
- **WHEN** Kafka 已确认接收消息，平台尚未获得业务处理结果
- **THEN** 查询显示已发布、业务处理结果未知，不计入业务处理成功数
