# Change: 采集结果派发与下游处理任务

## Why

当前业务方直接对接采集队列和 Kafka，采集团队维护结果投递。某次采集成功后，平台很难回答哪些服务应当收到结果、哪个服务已处理、哪个环节需要补跑。目标是让业务方和 Worker 通过 HTTP 完成日常操作，并能沿一条采集任务追踪到各个处理结果。

## What Changes

- 业务方按采集类型提交请求；平台解析队列、记录归属和业务请求 ID。采集 Worker 先写对象存储，再通过既有 ACK 协议提交轻量回执。
- 对启用结果派发的任务，以 MySQL 事务持久保存采集成功、回执、接收方快照和待派发记录，之后才确认 ACK。平台内部派发进程为每个授权接收服务和步骤创建独立的处理任务。
- 下游复用 HTTP 领取、续租、ACK、NACK 和死信机制。从任务中获得产物引用，无需直连 Redis、接入 Kafka 或注册回调地址。
- 新增父子任务追踪、定向补跑、业务统计及三段积压指标。为存量 Kafka 消费方提供平台内部兼容发布路径，按业务步骤逐个切换。

## Impact

新增能力为 `result-delivery`。依赖已实现的 `task-scheduling`、`task-dispatch` 和 `task-receipt`。其中 `task-receipt` 的异步刷盘约定继续适用于普通任务；启用本能力的采集和处理任务采用本提案的持久化确认约定。

实现涉及 HTTP 请求模型与身份授权、租约和 ACK、MySQL 迁移、Redis 就绪队列、后台派发、统计查询和迁移期 Kafka 发布。首版聚焦采集到独立处理步骤的一层扇出；通用工作流编排、Webhook 和容量压测均在本次范围之外。
