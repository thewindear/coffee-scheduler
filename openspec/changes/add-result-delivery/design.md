# 采集结果派发设计

## 一条任务的生命周期

商品业务提交采集任务 A。采集 Worker 保存文件并 ACK；平台在 MySQL 提交回执和两条待派发记录。派发进程为商品 ETL 创建任务 B，为质检创建任务 C。两个服务从各自的逻辑队列领取任务，读取同一版本的文件，提交自己的业务结果后 ACK。质检失败时，运维可以从 A 找到 C，复用原文件补跑质检。

| 数据 | 归属 | 关键内容 |
| --- | --- | --- |
| 采集任务 | 调度平台 | 任务 ID、业务归属、业务请求 ID、采集类型和状态 |
| 完成回执 | 调度平台 | 稳定的 `completion_id`、采集任务 ID、完成时间、摘要和版本化产物引用 |
| 产物 | 采集 Worker 写入对象存储 | 通过现有 `artifacts[].storage/uri/meta` 描述，格式和版本可放在 `meta`；在承诺的补跑窗口内可读取同一份内容 |
| 派发记录 | 调度平台 | 完成记录、接收服务、步骤、交付方式、派发状态及关联处理任务 ID |
| 处理结果 | 接收服务写业务库，平台记执行状态 | 每次执行对应的处理任务 ID、完成或失败时间、错误原因及补跑关系 |

## 接入契约

沿用 `/api/v1/tasks` 及其 `pull`、`heartbeat`、`ack`、`nack`。新接入业务按采集类型提交；平台从认证身份确定业务归属，从配置解析实际队列。下游拉取响应含处理任务 ID、来源采集任务 ID、完成记录 ID、步骤及产物引用。授权覆盖提交、领取、回报、查询、补跑和产物读取。逻辑队列名、`worker_id` 和 URI 均不作为授权凭证。

默认目的地是发起业务已配置的处理服务。附加接收服务须有授权规则。启用前检查默认路由完整性；采集完成时固定本次接收方、步骤及交付方式。规则更新仅影响后续完成记录。历史任务沿用原契约，只有显式接入的采集类型启用结果派发。

## 可靠交接与故障恢复

1. **接受 ACK。** 对接入链路的任务，为每次领取分配租约代次。MySQL 中保存可用于条件更新的当前执行代次；领取、回收和终态提交通过同一权威状态裁决。只有当前有效持有者可以完成任务。采集成功、回执和全部待派发记录在一个事务里提交。提交失败可重试；提交后响应丢失，凭同次执行及相同回执返回原确认。冲突回执不能替换已接受的回执。
2. **更新 Redis。** Redis 用于快速领取，队列和状态可从持久记录恢复。MySQL 已提交但 Redis 尚未更新时，以持久终态阻止再次执行。接入链路的异步查询投影须防止迟到的旧状态覆盖终态。该设计会给接入链路增加持久化开销，首版不承诺吞吐数字。
3. **创建处理任务。** 派发进程消费持久待办，以 `(completion_id, recipient_service, step)` 唯一约束正常派发。在同一数据库事务中创建可恢复的处理任务并关联派发记录，再投影至 Redis。派发进程在写库后、入队前退出，可用原处理任务 ID 重建就绪项。修复时核对当前代次和状态，避免将已完成或仍持有效租约的任务重新置为就绪。
4. **确认业务处理。** 下游缓慢或离线不影响其他接收服务。下游先以处理任务 ID 幂等提交业务结果，再 ACK；同一任务可能被重复领取。处理任务的成功或最终失败也要可持久查询。处理任务 ACK 到此结束，不再触发采集结果派发。

## 补跑与统计

租约超时和自动重试沿用同一处理任务 ID。显式要求重新处理时创建新的处理任务 ID，关联原任务与原完成记录，并记录运维请求的幂等键；这样下游可以区分重复投递与有意再次执行。重新采集则创建关联的新采集任务，保留原回执和历史。产物已过保留期或已确认删除时，返回可识别的不可补跑原因，由调用方决定是否重新采集。

通过采集任务 ID 返回授权范围内的交付清单、各处理任务状态、错误和补跑历史。采集成功数按采集任务计，处理成功或失败数按接收服务和处理任务计。自动重试次数单列，人工补跑可单独过滤。状态报表支持按业务方、服务及时间窗筛选；超时按配置的完成期限计算。

| 积压位置 | 计数单位 | 等待起点 |
| --- | --- | --- |
| 已到期、等待领取的采集任务 | 采集任务 | 本次进入就绪的时间 |
| 采集成功、接收方仍未获得可领取任务或 Kafka 尚未确认发布 | 接收服务和步骤的一条派发记录 | 采集成功时间 |
| 已就绪、等待下游领取 | HTTP 处理任务 | 本次进入就绪的时间 |

各段同时报告数量和最老等待时长。端到端超时从采集成功算到对应业务处理成功，包含已领取但尚未结束的处理。Kafka 兼容路径单列发布结果和可观测边界。

## 兼容与切换

Kafka 仅用于仍按原协议消费的业务。平台内部发布器使用固定的交付标识重试并保持原消息契约。Broker 确认后标记为已发布；缺少业务回报时，下游处理状态显示为未知。启用兼容发布器前须交接原采集端发布责任，避免两个发布方处理同一份结果。

每个接收服务的每个步骤只选 HTTP 处理任务或 Kafka 一条正式路径。切换前核对旧待办和已交付边界，按明确的完成记录边界启用新规则。切换或回退后，已有派发记录继续按其快照方式交付。先用一个业务验收完整链路，再逐业务迁移。保留期限、业务超时阈值和身份凭据接入方式由部署配置确定。
